# 任务批次时间窗口

在「脚本设置 → TaskWindows / 任务批次时间窗口」配置。`enabled=false` 为默认值，未启用时保持原调度。
任务列表使用英文任务名、逗号分隔；任务本身仍需要开启。第一版支持 DailyTrifles、AreaBoss、SoulsTidy、RichMan、WeeklyTrifles。

## 本机安排

| 批次 | 时间 | oas1 | oppo |
| --- | --- | --- | --- |
| 早间 | 每天 09:05–10:30 | DailyTrifles,AreaBoss | DailyTrifles,AreaBoss |
| 晚间 | 每天 21:05–22:00 | SoulsTidy | SoulsTidy |
| 每周 | 周一 09:05–11:00 | RichMan,WeeklyTrifles | RichMan |
| 补跑 | 每天 21:05–22:00 | 当天未完成日常、未完成周任务 | 同左 |

这些是允许**启动**的窗口，按电脑本地时区（本机北京时间）计算。开始包含、结束不包含；窗口内晚到可以启动，窗口结束时不强制中断正在运行的任务。早间任务超过窗口后进入晚间补跑；当天最后窗口关闭后，普通日常留到次日。周任务漏跑时，可在后续日期早间窗口或晚间补跑窗口执行，完成后到下一周再执行。关闭补跑后只使用各组主窗口。第一版不支持跨午夜窗口。

多个任务沿用当前调度顺序，不保证表格书写顺序。同一任务不能加入多个组。逢魔、狩猎、蹭卡、挂卡、悬赏等不在第一版支持列表中，继续沿用原调度。无需启用旧的 `task_hoarding_duration`。

## 下一次时间与完成记录

调度队列显示经过窗口计算的可启动时间，配置中的原始 `scheduler.next_run` 不因每次检查而改写。成功完成组内任务时，将下一次安排到下一个日/周批次的开始时间，替代该任务的成功间隔和强制服务时间；因此晚完成不会导致每天越跑越晚。失败不写完成记录，默认 10 分钟后在可用窗口重试，原有连续失败保护仍有效。

每个账号在 `config/task_windows/<账号>.json` 保存完成记录，使用文件锁和原子替换。停止和重启脚本后会继续尊重记录；不要删除该文件来排错，否则可能重新执行已完成的采购。记录损坏会报错，不会默默清空。已购买但尚未记录完成时发生进程中断，仍需依赖任务自身检查游戏剩余购买次数，无法保证游戏操作与本地记录的事务一致性。

总览/API 中 `next_run` 是可启动时间，另提供 `original_next_run` 和 `batch`（组、周期、窗口结束时间）供客户端使用。日志显示等待批次及启动批次信息。界面“立即运行”（清空时间或设为当前/过去）和 `task_call()` 可以一次性绕过窗口；安全休息规则仍然有效。单纯修改未来运行时间会继续受窗口限制。

## 切换与验证

本次配置迁移备份放在 `config/task_windows/backups/`。迁移保留原定运行日期，将组内任务时刻对齐到主窗口；不会将下周的采购提前到本周。以后成功运行后自动按批次日历安排。

代码更新后需要重启整个 OAS 后端/界面和两个账号的脚本进程，以加载新配置模型与调度代码。运行旧代码的进程会在保存时丢弃不认识的新字段，因此本次最终配置暂存在 `config/task_windows/pending/<账号>.json`。新版本脚本循环启动时自动应用、备份账号配置，然后删除暂存文件；应用时读取最新的任务日期，不覆盖任务运行期间的其他设置变化。重启后确认 TaskWindows 开关与列表仍正确。

测试命令（PowerShell）：

```powershell
$env:PYTHONIOENCODING='utf-8'
.\toolkit\python.exe -m unittest discover -s tests/module -p test_task_windows.py
```

测试不连接模拟器、不执行购买或战斗。首次实机观察应检查：窗口外等待、到时启动、结束后下次时间、重启后不重复四个行为。
